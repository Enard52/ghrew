## Что пользователь хотел и почему архитектура получилась такой

Изначальная идея: экспериментальный командный чат на GitHub Discussions,
статический клиент на Pages, без постоянного внешнего сервера. GitHub Actions
используется как обработчик запросов вместо постоянно работающего backend.

Критичное требование: **один приватный `gitwok-vault` для всех приватных каналов
и DM, доступ к репозиторию в GitHub только у администраторов**. Остальным
участникам выдаётся доступ к конкретным разговорам через приложение.

Вариант логин/пароль обсуждался, но не реализован. В текущей версии каждый
участник входит своим GitHub-аккаунтом. RxDB обсуждался, но не включён.
Cloudflare Worker для старого OAuth-входа остался как необязательный fallback;
новый путь входа и vault используют Actions.

Пользователь неоднократно указал, что установка непонятна и слишком сложна.
Нельзя снова описывать нынешний процесс как установку «в один клик» или
считать рабочую демку доказательством готовности самостоятельной установки.

## Архитектура сейчас

Организация GitHub соответствует workspace. Репозиторий исходников продукта
и репозитории разговоров — разные ресурсы.

| Ресурс пространства | Видимость | Назначение |
| --- | --- | --- |
| `gitwok-chat` | Public | Публичные каналы в Discussions; сообщения и треды |
| `gitwok-vault` | Private | Все приватные каналы и DM; каталог участников и ACL |
| `gitwok-auth` | Public | Зашифрованные запросы и ответы через Issues; workflow Actions |
| `gitwok-client` | Public, опционально | Независимая копия клиента и свой Pages |

```text
Статический Nuxt-клиент
  ├── пользовательский токен → публичные Discussions / Issues / Projects
  └── зашифрованная issue → GitHub Actions
                              ├── Device Flow → зашифрованная сессия
                              └── проверка участника и ACL → приватный vault
                                                           ↓
                                             зашифрованный ответ в issue
```

Actions — серверное исполнение с очередью. Здесь нет WebSocket realtime,
присутствия или typing. Публичные сообщения обновляются примерно раз в 20 секунд,
приватные — раз в две минуты или вручную. В живых проверках отдельные приватные
операции занимали десятки секунд; это не гарантия времени ответа.

## Sandbox и существующие ресурсы

Пользователь создал организацию **`gitwok-sandbox`**, после чего в ней были
настроены три сервисных репозитория и отдельная публичная App.

- Сайт: <https://gitwok.inchi.dev/>.
- Прямая ссылка на sandbox:
  <https://gitwok.inchi.dev/?auth=gitwok-sandbox/gitwok-auth&workspace=gitwok-sandbox/gitwok-chat>.
- Мастер создания своего пространства: <https://gitwok.inchi.dev/create/>.
- Исходники остались в `inchidev/gitwok`.
- Старый рабочий стенд `inchidev/gitwok-chat`, `inchidev/gitwok-auth`,
  `inchidev/gitwok-vault` сохранён. Данные не удалялись и не переносились в sandbox.

В новой организации перед настройкой был проверен пустой список репозиториев;
базовый доступ выставлен в `None`. На последней проверке единственный GitHub
collaborator vault — `vnmtvlv`, администратор. Ранее базовый доступ `inchidev`
тоже был изменён на `None` с отдельного согласия пользователя после аудита.

Sandbox использует публичную App, которую могут авторизовать пользователи вне
организации. Им не требуется вступать в GitHub-организацию или получать доступ
к vault. Обычная установка команды по умолчанию создаёт приватную App;
авторизовать её могут участники организации-владельца.

Открытая регистрация включена явно в приватном `.gitwok/members.json`:

- `openRegistration: true` разрешает операцию `join`.
- `memberPrivateChannels: true` разрешает участникам создавать приватные группы.
- `join` берёт ID и login из настоящего GitHub issue event, а не из payload.
- Перед регистрацией проверяются GitHub-доступы vault.
- Вступление не даёт роль администратора и доступ к существующим разговорам.
- Удалённый участник попадает в `blocked` и не может самостоятельно вступить
  заново. Явное приглашение администратором снимает блокировку.
- Флаги в публичном config включают клиентский сценарий; полномочия определяет
  приватный каталог участников на стороне Actions.

Creator создаёт репозитории, записывает workflows и Secrets и при необходимости

На последней проверке Creator установлен в `inchidev` только на `gitwok-auth`.
Новые администраторы устанавливают Creator в свою организацию сами.

Права Creator: repository Administration, Contents, Workflows, Secrets, Actions,
Pages, Discussions — write; organization Members и Administration — read.
Чтение Organization Administration понадобилось, чтобы API возвращал базовые
права организации; без него поле было `null`, и установщик останавливался.
Variables permission из manifest убрали как неподдерживаемый вариант;
собственный клиент получает публичный `gitwok-client.json`.

Права workspace App: Contents, Issues, Discussions — write; Metadata,
pull requests, organization Projects — read. App установлена только на три
сервисных репозитория соответствующего пространства.

Старые App `gitwok-chat` и OAuth Worker сохранены для legacy-пути. Не удалять
их автоматически при переименовании продукта.

## Как пользователь проходит вход и установку

### Попробовать sandbox

1. Открывает sandbox и нажимает Continue with GitHub.
2. Отправляет подготовленную sign-in issue на GitHub.
3. Возвращается в клиент, получает device code.
4. Вводит код на GitHub и подтверждает авторизацию тем же аккаунтом.
5. Клиент получает зашифрованную сессию и отправляет `join`.

Вход через issue и код — осознанный обход отсутствия постоянного OAuth-сервера,
но существенная проблема UX. Мастер установки сам по себе её не устраняет.

### Создать пространство своей команды

1. Открывает `/create/` до входа в чат.
2. Устанавливает GitWok Creator в целевую организацию и авторизует его через
   общий служебный mailbox.
3. Указывает организацию и выбирает общий фронтенд или собственный Pages.
4. Установщик проверяет владельца, базовые права `None` и занятость имён;
   создаёт репозитории и предлагает регистрацию собственной App через manifest.
5. Администратор подтверждает создание App, вручную включает Device Flow,
   устанавливает её только на три сервисных репозитория.
6. Проходит Test my workspace sign-in уже через свою App.
7. Мастер проверяет администратора, обращение к vault через Actions и публичные
   Discussions. Для своего Pages установка также ждёт успешный workflow
   соответствующей ревизии.
8. Открывает пространство и после проверки может удалить Creator из организации.

Таким образом, сейчас есть два входа и несколько подтверждений GitHub.
Ключи не нужно скачивать или вручную копировать в Secrets, терминал необязателен.
Есть и CLI: `npm run setup -- --organization YOUR_ORG --own-client`.

Мастер восстанавливает этап после reload в той же вкладке. Закрытие вкладки
посреди регистрации может потерять recovery material. Это ограничение остаётся;
не обещать восстановление после любого прерывания. Чужие репозитории установщик
не перезаписывает; повторные попытки используют installation markers.

## Доверие и приватность

- Общий фронтенд получает пользовательский токен и расшифрованные сообщения.
  Возможность обновлять JavaScript означает необходимость доверять оператору сайта.
- Свои репозитории при общем фронтенде не дают полной независимости.
- Собственный Pages позволяет контролировать клиентский код и обновления.
  Для независимости нужно также отозвать доступ Creator после настройки.
- Workspace App private key и mailbox private key сохраняются в Actions Secrets
  соответствующего `gitwok-auth`: `GITWOK_APP_PRIVATE_KEY`, `MAILBOX_PRIVATE_KEY`.
- Vault installation token создаётся на короткое время, ограничивается vault,
  отзывается после операции и не передаётся браузеру.
- Пользовательский токен живёт в `sessionStorage`, до восьми часов. Refresh token
  в mailbox-режиме отбрасывается; logout очищает сессию и удалённые кеши.
- Администраторы пространства и GitHub могут читать приватные разговоры и DM.
  Это не E2EE против них.
- Mailbox использует P-256 ECDH и AES-GCM с привязкой к request ID. Публичны
  пользователи, время, классы запросов и размеры ciphertext. Forward secrecy нет.
- `artifacts/` и `.gitwok-setup/` — ignored служебные файлы; там могут находиться
  временные сессии или recovery material. Не включать их содержимое в коммиты
  и документы. Здесь секреты не записаны.

Последняя версия прошла **36 unit tests и 13 Playwright-сценариев**, typecheck,

- [Main CI](https://github.com/inchidev/gitwok/actions/runs/38573812338).
- [Pages deployment](https://github.com/inchidev/gitwok/actions/runs/38573829973).

Живые проверки под аккаунтом `vnmtvlv` подтвердили:

- Device Flow новой App и получение сессии с правильным immutable GitHub ID.
- Точный доступ App к трём репозиториям и admin-only доступ к vault.
- Sandbox join для уже существующего администратора, каталог участников,
  создание приватного канала, отправку и чтение, правильное авторство.
- На опубликованном сайте: анонимную входную страницу, `/create/`, direct reload,
  телефонную компоновку, публичное и приватное чтение через реальную сессию,
  выход с очисткой сообщений и токена. Прямых REST-запросов браузера к vault
  проверка не обнаружила.
- Навигацию и reload мастера в локальной сборке с Pages-префиксом
  `/gitwok-client/`.

Исправленная проблема доставки: GitHub кешировал пустые ответы comments до
60 секунд. Клиентский опрос mailbox теперь использует `cache: "no-store"`;
добавлен regression test.

**Не проверено живьём:** вход независимого второго аккаунта, реальные DM между
двумя людьми, полный browser-install новой команды с Creator и её собственным
Pages. Mocked E2E и проверки ролей в unit tests не заменяют эти сценарии.

локально. Template копирует код, но не Discussions и Secrets; автоматических
upstream-обновлений своей копии пока нет.

## С чего продолжить обсуждение

1. Объединить этот технический baseline с новым направлением Ghrew, не выдавая
   планируемые агенты или backend за уже работающую функциональность.
2. Решить, сохраняем ли GitHub-only эксперимент или допускаем небольшой backend
   ради нормального OAuth-входа и более простой установки. Новая архитектура
   ещё не реализована; исходная независимость команды остаётся важным критерием.
3. Пройти текущий sandbox вторым независимым аккаунтом и полный мастер новой
   команды. Фиксировать каждый непонятный шаг и ручное вмешательство.
4. Отдельно спланировать rename кода, remote, доменов, Apps и служебных репозиториев.
   Не переименовывать живые ресурсы только потому, что изменилось имя папки.
